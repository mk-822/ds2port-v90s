# 表示性能の測定

PlumOS V90S V2実機で、FLOATを実行しながら640×480・32bitの画面取得とフレームバッファ転送を測定しました（2026-10-23）。各方式8秒、通常のfbbridgeを一時停止し、同じ画面経路へ測定プログラムだけが書き込む条件です。

| 方式 | 画面転送fps | 取得時間/フレーム | コピー時間/フレーム |
| --- | ---: | ---: | ---: |
| 従来：XGetImage、コピー後に33ms待機 | 16.78 | 8.387ms | 17.054ms |
| XGetImage、コピー最適化、60Hz周期 | 59.66 | 7.875ms | 1.803ms |
| XShmGetImage、コピー最適化、60Hz周期 | 59.61 | 1.787ms | 1.703ms |

従来はmemcpy後、フレームバッファ上の画素を読み戻してアルファ値を付けていました。この領域の読み戻しが遅いため、CPU側の画像へアルファ値を付けながら一度だけ書き込む方式へ変更しました。待機も毎回33msを足す方式から、処理時間を含めた周期制御へ変更しています。

X11 MIT-SHMが利用できる場合は共有メモリーを再利用し、毎回の画像受信・確保を減らします。拡張が無い場合や利用できない場合はXGetImageへ自動で戻ります。

組み込み後の実ゲームでは転送約60fps、取得約1.9ms、コピー約1.9msを確認しました。ユーザーからも滑らかさの改善、Bクリック、Y/R2加速、電源メニューからの復帰に問題がないことを確認済みです。カーソル移動量は経過時間から計算し、表示速度が上がっても移動速度が比例して増えないようにしています。

ここでいうfpsは画面の取得・転送回数です。ゲーム内部の更新頻度を60fpsに変更するものではありません。ログの `sampled_changes_s` は画像の一部をサンプリングした変化回数で、ゲーム内部のfpsを厳密に計測する値でもありません。

## PowerVR

本体のドライバーで次を確認しました。

- EGL 1.4、Imagination Technologies
- PowerVR Rogue GE8300、OpenGL ES 3.2
- オフスクリーン描画とピクセル読み戻し成功、GLエラーなし

今回はCPU側の転送改善で約60fpsへ到達したため、ゲームの表示経路にEGL/GPUは追加していません。GPUによる最終表示やDirectDrawの処理変更は今後の別検証です。Box64上のゲーム処理は引き続きCPUで実行します。

## 再検査

SDK内で以下をビルドできます。

```sh
gcc -O2 -Iruntime/native tests/frame-benchmark.c -o bld/frame-benchmark -lX11 -lXext
gcc -O2 -Iruntime/native tests/capture-smoke.c -o bld/capture-smoke -lX11 -lXext
gcc -O2 tests/egl-probe.c -o bld/egl-probe -lEGL -lGLESv2
```

`frame-benchmark ximage legacy`、`frame-benchmark ximage deadline`、`frame-benchmark shm deadline` を本体の実行環境変数の下で実行します。測定中は通常のfbbridgeを停止し、終了時に必ず再開してください。フレームバッファへ書き込むため、電源メニューと同時実行しないでください。

`capture-smoke shm` と `capture-smoke ximage` は各64フレームの取得・解放を確認します。別のXvfbを `-extension MIT-SHM` 付きで起動した環境では `capture-smoke fallback` も確認できます。これらの取得検査はフレームバッファへ書き込みません。実機で3方式すべて成功し、二重解放の検査も通しています。

診断用の環境変数は `DS2PORT_CAPTURE=ximage` で共有メモリーを無効化、`DS2PORT_FPS` で転送周期（標準60、範囲10～120）、`DS2PORT_CURSOR_SPEED` で通常カーソル速度（標準120px/秒）を変更できます。Y/R2加速時はこの速度の2倍です。

## ダブルバッファと垂直同期

本体のフレームバッファは640×960、32bit、2,457,600バイトで、640×480の画面を2枚持てます。非表示のページへ描いてから `FBIOPAN_DISPLAY` と `FB_ACTIVATE_VBL` で表示ページを切り替える方式を追加しました。連続20回のページ切替は約16.8～16.9ms周期で待機し、ゲーム実行時も約59fpsで安定しています。表示周期の待ち時間はログの `present_ms` に分けて記録します。

`FBIO_WAITFORVSYNC` はこの本体では成功を返しても0.002～0.010ms程度で戻り、垂直同期待ちとして機能しません。今回の実装ではこれを同期根拠にせず、実際に待機するページ切替を使用します。

ページ数・メモリー範囲・パン機能が足りない場合や切替が失敗する場合は、従来の表示ページへの転送に戻ります。`DS2PORT_PRESENT=single` で明示的に無効化することもできます。電源メニューからの再開時には実際の表示ページを再取得します。

ユーザーがFLOATの表示・操作・電源メニュー復帰を確認済みです。切替待ちを含むfbbridgeの短時間CPU使用率は1コア換算15.8%でした。ログの `present_ms` 約12.5～12.8msは待機を含む経過時間で、同じ長さのCPU計算を追加しているわけではありません。

診断プログラムは `gcc -O2 tests/fb-sync-probe.c -o bld/fb-sync-probe` でビルドできます。引数なしでVSync ioctlの待機時間を確認し、`pan` を付けると同じ画像を両ページへ置いて切替・復元します。実行中は通常のfbbridgeを停止し、終了時には元のpan値とブリッジを復元する必要があります。

## コア分散と音源負荷

ゲーム、Xvfb、fbbridge、sb16-synthは独立プロセスです。本体の4コアすべてで実行可能な状態になっており、追加のスレッド分離なしでもOSが並列に動かせます。コアへの固定はしていません。

FLOAT実行中のある場面を5秒間計測した、1コアを100%とするプロセスCPU使用率は次のとおりです。ゲーム場面・周波数・音数で変動します。

| プロセス | CPU使用率 | スレッド数 |
| --- | ---: | ---: |
| FLOAT.EXE | 112.2% | 7 |
| Xvfb | 15.2% | 1 |
| fbbridge（単一表示ページ版） | 15.0% | 1 |
| sb16-synth | 13.2% | 1 |

スレッド分離やコア固定は処理の競合・遅延のばらつきを減らす手段であり、音声合成などの計算量そのものを減らす手段ではありません。

libADLMIDI 1.5.1でDOSBoxとNukedの両コアを有効にした測定専用ビルドも比較しました。1チップ・バンク58・12音・44.1kHzで、ウォームアップ後に20.004秒分をオフライン合成した結果です。

| OPL3コア | 合成CPU時間 | 実時間再生換算の1コア負荷 |
| --- | ---: | ---: |
| DOSBox | 0.734秒 | 3.67% |
| Nuked | 4.636秒 | 23.18% |

このビルドと条件ではNukedの合成CPU時間は約6.3倍でした。ALSA出力・MIDI処理・音量処理などを含まないため、前述の実プロセス使用率13.2%とは条件が異なります。現行のDOSBoxコアは変更していません。

libADLMIDIはOPL3用MIDIシンセサイザーで、Nukedはその内部で選べるエミュレーションコアでもあります。[公式資料](https://github.com/Wohlstand/libADLMIDI)でもDOSBoxは高速、Nukedは高精度でCPU負荷が高いと説明されています。[libOPNMIDI](https://github.com/Wohlstand/libOPNMIDI)はOPN2/YM2612系の別音源で、SB16のOPL3とは音色もチップ構成も異なります。その実機負荷は今回未計測で、OPL3との優劣は断定していません。

音源比較のソースは `tests/opl-benchmark.cpp` です。DOSBox・Nukedを有効にした同じlibADLMIDIへリンクして実行すると、音声出力を変更せずCPU時間と生成サンプルのエネルギーを取得できます。

## BGMの音程と出力レート

ユーザーからBGMの音程が高いとの指摘があり、音源の生成・ALSAの設定だけでなく、実際のPCM消費速度も調べました。

修正前はlibADLMIDI、PCM入力、dmix、カーネルのhw_paramsすべてが44,100Hzを示していました。しかし無音を追加する診断では44,100Hz入力が実際には約47,613.8フレーム/秒で消費され、カーネルのDMAポインターからの独立計測でも約47,611.6フレーム/秒でした。この比率では音程が約1.33半音上がります。設定表示だけでは実際の再生速度を判断できない状態でした。

物理出力とdmixを48,000Hzへ変更し、外側のALSA plugで44,100Hz入力を48,000Hzへリサンプリングする構成に修正しました。変更後の同じ診断では、44,100Hz入力の消費速度が約44,062.2フレーム/秒となり、設定値との差は約0.09%に収まりました。ユーザーもhero3で音程が自然な高さへ戻ったことを確認しています。音源の音符を移調する補正は行っていません。

両ゲームの既存設定へ反映し、転送用テンプレートも修正しています。音量処理、音源コア、音色バンクは維持しています。

`tests/audio-rate-probe.c` は現在のdefault PCMへ無音を加え、ウォームアップ後の書込フレーム数・開始終了時の遅延・単調増加時計から消費速度を計算します。`gcc -O2 tests/audio-rate-probe.c -o bld/audio-rate-probe -lasound` でビルドできます。本体で対象ゲームと同じ環境変数の下で実行してください。PCM設定のダンプも出力するため、リサンプリング段の有無を確認できます。

`tests/opl-pitch-probe.cpp` は現在の音源コア・バンク・Win9x周波数モデルでMIDIノート69を生成し、出力段を通さないデータを作ります。今回の解析では複数の音色で約437.1Hzを検出し、合成段階に約1半音の上ずりがないことも切り分けました。生成データはGitに含めません。
